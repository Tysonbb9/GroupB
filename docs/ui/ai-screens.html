Crunch Week: the AI screens

Three screens for what the model does, before any of it is built (issue #123). The rule from docs/DESIGN.md section 1 holds everywhere on this page: the model never produces a number. It decides what to ask, when to ask, and in what shape. Code decides what is true. So on every screen below, the model chose a question or a set of fields — and every hour, date, percentage and grade came out of a tested function. Nothing here is a chat box: the model renders structured fields, and the student confirms or fixes them.

Style is Option A from issue #96 (tabs, one focus per screen), matching docs/ui/layout-proposals.html. Sample data is the app's own (Fall 2026, week 3 of 15, 12 of 15 hours this week, the wall at week 6). Mockups, not code.

What you see first

  • Three blocks of fields — assignments, weights, policies — each with a tick or a Fix. No summary paragraph to read.
  • One line is red because code rejected it, not because the model felt unsure.

Who did what

  • Model: chose which fields to render, filled them from the page, and marked the two it could not read confidently.
  • Code: week must be 1–15, hours 0–100 or blank, weights must sum to 100%. The Add to semester button is disabled while a field is red. The model cannot talk past this.

Reused from US-30

  • The assignment drafts are the existing review boxes (title / week / hours / Remove) and the existing error copy, unchanged.
  • Weights and policies are new: they exist in the data model as of Phase 3 but have never had a screen.

Undated lines

  • "Weekly quizzes" with no dates is the honest limit DESIGN.md section 2 names. The model renders it as a weekly item with blank hours and says so in one line — it does not invent a date.

Build effort

  • Medium. The review step exists; this adds two field blocks and a weights-sum check. No new screen.

Trade-offs

  • Weights and policies are fields the student may not know off-hand; the tick lets them accept a good read quickly.
  • A wrong weight silently distorts a later grade figure, which is why the sum check sits on screen rather than in a warning list.

What you see first

  • One question, one line of why now, two buttons. It sits above the figures because the answer can change them.
  • Answering "Yes" dismisses it and the model asks nothing else about CS 262 for a while.

Who did what

  • Model: noticed its picture of CS 262 went stale, picked this course and this week out of five, and chose to render three candidate changes rather than a free-text box.
  • Code: recomputed every hour on screen from the saved fields. The 24 in the banner is the forecast function running again, not the model estimating.

Why one question

  • Five courses asked at once is a form nobody finishes. One question, at most a few a week, is the version that gets answered.
  • "None of these" tells the model its picture is wrong somewhere it cannot see — useful, and it stops asking that question.

Build effort

  • Medium. A card on the Forecast tab, one answer endpoint, and a place to store when a course was last confirmed.

Trade-offs

  • A question above the figures costs the student attention daily. Rate-limiting it is a code rule, not a model judgement.
  • The candidate changes shown after "Something changed" are guesses; the student still has to correct them, which is the point — but a wrong guess list can feel like being talked at.

What you see first

  • A normal notification: one course, one action, one number, and a count of how many today.
  • The settings screen splits into two kinds of rule: padlocked (code) and switchable (yours).

Who did what

  • Model: decided tonight deserves a reminder about the demo, and phrased it in one line.
  • Code: the daily count, the class-time check against the timetable, and the dedup against anything already reminded. If any of the three fail, the notification is dropped and the model never learns it was suppressed — it has no authority to retry.

Why the count is on the notification

  • "1 of 2 today" makes the limit visible instead of trusting it. It is a code figure, so it can be tested.

Build effort

  • Large. Push infrastructure, a timetable to be silent against, and a record of what has already been reminded. This is why it is the optional screen.

Trade-offs

  • Showing "1 of 2" invites the student to ask for the second one; there is no button for that, on purpose.
  • Class-time silence needs a timetable the app does not have yet — it would come in with the schedule feed, not with this card.

Not shown, on purpose: a chat box. DESIGN.md section 3 leans against one, and none of these screens needs it — every interaction above is a field, a tick, or a two-button answer. Running grades are out of scope (input 08 is deferred), so no screen here shows a percentage score for the student, only the weights a syllabus states.
